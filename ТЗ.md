# Технічне завдання: ArenaMaster

## Платформа для організації кіберспортивних турнірів

**Версія:** 1.0  
**Дата:** 29.05.2026  
**Статус:** Чернетка

---

## 1. Загальний опис проєкту

### 1.1 Назва

ArenaMaster — веб-платформа для організації, проведення та відстеження аматорських кіберспортивних турнірів.

### 1.2 Мета

Надати зручний інструмент для аматорських гравців та невеликих ігрових спільнот для самостійного створення і проведення онлайн-турнірів без потреби у сторонніх сервісах.

### 1.3 Цільова аудиторія

- Аматорські гравці, які хочуть змагатись з друзями або в рамках своєї спільноти.
- Невеликі ігрові клуби, стримери, організатори локальних подій.
- Адміністратори платформи, які модерують контент та користувачів.

### 1.4 Підтримувані дисципліни

Платформа є мультиігровою. При створенні турніру організатор вказує дисципліну вручну (назва гри). Із сідером заповнюються такі дисципліни:

- Counter-Strike 2
- Dota 2
- Valorant
- League of Legends
- FIFA / EA FC

### 1.5 Мова інтерфейсу

Українська (основна). Контент (назви команд, ніки) — будь-якою мовою.

## 2. Ролі користувачів

| Роль        | Опис                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------- |
| Гравець     | Зареєстрований користувач. Може брати участь у турнірах, вступати до команд, переглядати профілі. |
| Організатор | Може створювати турніри, керувати їх налаштуваннями та брекетом.                                  |
| Адмін       | Повний доступ до адмін-панелі: управління користувачами, турнірами, командами, дисциплінами.      |

Один обліковий запис може мати лише одну роль. Адмін призначається вручну через базу даних або через адмін-панель іншим адміном.

## 3. Функціональні вимоги

### 3.1 Автентифікація та авторизація

- Реєстрація через форму (email + пароль) з підтвердженням email.
- Вхід через форму (JWT access token + refresh token).
- OAuth через Google та Discord (опціонально при реєстрації).
- JWT зберігається в httpOnly cookie (access — 15 хв, refresh — 7 днів).
- Захищені маршрути перевіряють токен на кожен запит.
- При OAuth — якщо email вже існує, акаунти зв'язуються автоматично.

### 3.2 Профіль гравця

Публічна сторінка гравця містить:

- Аватар (завантажується з Unsplash або власне фото).
- Нікнейм, короткий опис (bio).
- Посилання на Discord та інші соціальні мережі (до 3 посилань).
- Статистика: кількість турнірів, перемог, матчів зіграних.
- Історія участі у турнірах (список із результатами).
- Команди, до яких належить гравець.

Редагування профілю доступне лише власнику.

### 3.3 Команди

#### Створення команди

- Капітан (гравець, який створює команду) вводить назву та завантажує логотип.
- Логотип завантажується з Unsplash або власне зображення (файл).
- Один гравець може бути капітаном лише однієї команди.
- Один гравець може бути членом кількох команд.

#### Управління складом

- Капітан надсилає запрошення гравцям за нікнеймом або email.
- Гравець отримує сповіщення і може прийняти або відхилити запрошення.
- Капітан може виключати членів.
- Ролі в команді: `captain` (1 особа), `member`.

#### Публічна сторінка команди

- Назва, логотип, дата створення.
- Список учасників із посиланнями на профілі.
- Статистика команди: кількість турнірів, перемог.
- Останні результати в турнірах.

### 3.4 Турніри

#### Створення турніру (організатором)

Поля для заповнення:

| Поле            | Тип        | Опис                                                        |
| --------------- | ---------- | ----------------------------------------------------------- |
| Назва           | рядок      | Назва турніру                                               |
| Дисципліна      | рядок      | Назва гри                                                   |
| Формат          | enum       | `single_elimination`, `double_elimination`                  |
| Тип учасників   | enum       | `solo` (1v1), `team`                                        |
| Розмір команди  | число      | Кількість гравців у команді (лише для типу `team`)          |
| Дата початку    | datetime   | Коли починається турнір                                     |
| Дата реєстрації | datetime   | Дедлайн подачі заявок                                       |
| Макс. учасників | число      | Степені двійки: 4, 8, 16, 32                                |
| Призовий фонд   | текст      | Опис нагород (1, 2, 3 місце)                                |
| Опис            | текст      | Правила, умови участі                                       |
| Обкладинка      | зображення | Завантажується з Unsplash (автоматично) або файл            |
| Стрім-лінк      | url        | Посилання на трансляцію (необов'язково)                     |
| Статус          | enum       | `draft`, `registration`, `ongoing`, `finished`, `cancelled` |

---

#### Реєстрація на турнір

- Гравець або капітан команди подає заявку на участь.
- Для турнірів типу `solo` — реєструється окремий гравець.
- Для турнірів типу `team` — капітан реєструє команду (склад фіксується на момент реєстрації).
- Організатор може підтверджувати або відхиляти заявки вручну, або увімкнути автоматичне прийняття.
- Повторна реєстрація після відхилення — заборонена.
- Після досягнення ліміту `max_participants` реєстрація закривається автоматично.

#### Статуси турніру

```
draft -> registration -> ongoing -> finished
                     \-> cancelled
```

- `draft` — турнір збережено, але не опубліковано.
- `registration` — відкрита реєстрація учасників.
- `ongoing` — турнір розпочато, брекет згенеровано, матчі проводяться.
- `finished` — всі матчі завершено, визначено переможця.
- `cancelled` — турнір скасовано організатором або адміном.

Перехід зі статусу `registration` до `ongoing` — вручну організатором. При цьому автоматично генерується брекет.

#### Генерація брекету

**Single Elimination:**

- Учасники розподіляються по брекету випадково (або за сідингом, якщо вказано).
- Кількість раундів: `log2(max_participants)`.
- Переможець матчу переходить до наступного раунду.
- Фінальний матч визначає переможця турніру.

**Double Elimination:**

- Дві сітки: Winners Bracket та Losers Bracket.
- Програш у Winners Bracket переміщує учасника до Losers Bracket.
- Програш у Losers Bracket — вибування.
- Фінал: переможець Winners vs переможець Losers (Grand Final).
- При перемозі переможця Losers Bracket відбувається Reset-матч.

#### Матчі

Кожен матч має:

| Поле            | Опис                                        |
| --------------- | ------------------------------------------- |
| `participant_1` | Перший учасник / команда                    |
| `participant_2` | Другий учасник / команда                    |
| `score_1`       | Рахунок першого                             |
| `score_2`       | Рахунок другого                             |
| `winner`        | Посилання на переможця                      |
| `round`         | Номер раунду                                |
| `bracket_side`  | `winners`, `losers`, `grand_final`          |
| `scheduled_at`  | Запланований час                            |
| `played_at`     | Фактичний час проведення                    |
| `status`        | `pending`, `ongoing`, `finished`, `no_show` |

- Результат матчу вносить організатор або адмін.
- Після внесення результату система автоматично оновлює брекет (переміщує переможця у наступний матч).
- Редагування результату — лише до завершення турніру, лише організатором або адміном.

#### Призовий фонд

- Організатор описує призи у вільному текстовому полі (наприклад: "1 місце — 500 грн, 2 місце — 200 грн").
- На сторінці турніру призи відображаються у структурованому вигляді (місце + опис).
- Система не обробляє реальні платежі — лише відображення інформації.

#### Стрім-лінк

- Організатор може вказати одне посилання на трансляцію (YouTube, Twitch тощо).
- Посилання відображається на сторінці турніру під час статусу `ongoing`.

### 3.5 Сповіщення (in-app)

Сповіщення зберігаються у базі даних та відображаються у шапці сайту (лічильник + список).

| Подія                                             | Отримувач      |
| ------------------------------------------------- | -------------- |
| Запрошення до команди                             | Гравець        |
| Прийнято / відхилено у турнір                     | Учасник        |
| Турнір починається (статус змінився на `ongoing`) | Всі учасники   |
| Результат матчу внесено                           | Учасники матчу |
| Виключено з команди                               | Гравець        |

Сповіщення позначаються як прочитані при кліку або через кнопку "Позначити всі прочитаними".

---

### 3.6 Адмін-панель

Доступна лише користувачам з роллю `admin`. Розділи:

- **Користувачі** — перегляд, блокування, зміна ролі, видалення.
- **Турніри** — перегляд усіх турнірів, зміна статусу, видалення.
- **Команди** — перегляд, розпуск команди, видалення.
- **Дисципліни** — CRUD для списку ігор (використовується як довідник у формах).

## 5. Архітектура бекенду

### 5.1 Принципи

- **Проста архітектура** — без DDD, CQRS, Mediator.
- Логіка пишеться безпосередньо в обробниках маршрутів (handlers).
- Кожен handler — окремий метод або лямбда у відповідному файлі ендпоінтів.
- Спільна логіка (генерація брекету, хешування) виноситься у статичні хелпер-класи або extension methods.

### 5.3 Program.cs — підключення

У `Program.cs` реєструються:

1. DbContext з PostgreSQL connection string.
2. JWT Bearer автентифікація.
3. OAuth провайдери (Google, Discord).
4. FluentValidation.
5. CORS policy.
6. Статичні файли з теки `uploads/`.
7. Scalar (документація).
8. Усі групи ендпоінтів через extension методи.

### 8.3 Redux Store

```
store
├── auth         ← authSlice: { user, token, status }
├── notifications ← notificationsSlice: { items, unreadCount }
└── api          ← RTK Query: baseApi + всі ін'єктовані апі
```

- `authSlice` зберігає дані поточного користувача після логіну.
- `baseApi` налаштований з `baseUrl: import.meta.env.VITE_API_URL` та автоматичним додаванням `Authorization: Bearer <token>` заголовку.
- Refresh token логіка реалізована через `baseQueryWithReauth` (обгортка над `fetchBaseQuery`).

## 12. Безпека

### 12.1 Автентифікація

- Паролі хешуються BCrypt (work factor 12).
- JWT підписується симетричним ключем (HS256), ключ — у змінних середовища.
- Access token живе 15 хвилин, refresh token — 7 днів.
- Refresh token зберігається у БД, при logout — відкликається.
- При виявленні підозрілого повторного використання відкликаного токена — відкликаються всі токени юзера.

### 12.2 Авторизація

- Кожен захищений ендпоінт перевіряє JWT через middleware.
- Перевірка ролі виконується всередині handler (не через атрибути, щоб відповідати простій архітектурі):

```csharp
if (currentUser.Role != "admin") return Results.Forbid();
```

- Перевірка власності ресурсу (наприклад, чи є юзер організатором турніру) — також у handler.

### 12.3 Валідація

- Всі вхідні DTO валідуються через FluentValidation.
- При помилці валідації повертається `400 Bad Request` з деталями.
- Файли: перевірка розміру (макс. 5 МБ), типу (лише `image/jpeg`, `image/png`, `image/webp`).

### 12.4 OWASP

| Загроза                   | Захист                                        |
| ------------------------- | --------------------------------------------- |
| SQL Injection             | EF Core параметризовані запити                |
| XSS                       | React екранує вивід за замовчуванням          |
| CSRF                      | JWT у cookie з `SameSite=Strict`              |
| Broken Access Control     | Перевірка ролі та власності у кожному handler |
| Security Misconfiguration | CORS обмежений до домену фронтенду            |
| Sensitive Data Exposure   | Паролі не повертаються в DTO, JWT ключ у env  |

## 13. Нефункціональні вимоги

### 13.1 Продуктивність

- Відповідь API для спискових ендпоінтів — до 300 мс при 100 одночасних запитах.

- Індекси у БД: на `email`, `username`, `slug` (унікальні), на `tournament_id` у `matches`, `tournament_participants`.

### 13.2 Адаптивний дизайн

- Підтримка розширень: 320px (mobile), 768px (tablet), 1280px+ (desktop).
- Mantine breakpoints використовуються у CSS Modules:

```css
@media (max-width: 768px) { ... }
```

- Брекет турніру на мобільному — горизонтальний scroll.
- Адмін-панель — доступна з tablet+, на mobile відображається попередження.

### 13.3 Доступність

- Усі інтерактивні елементи доступні з клавіатури.
- Mantine забезпечує базову ARIA-підтримку.
- Кольоровий контраст відповідає WCAG AA.
